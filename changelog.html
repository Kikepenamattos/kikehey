📋 Protocolo de Push y Actualización de Changelog

▼

Documentación completa del proceso que se ejecuta cada vez que se solicita hacer push al repositorio y actualizar el changelog. Este protocolo garantiza que cada commit genere una card única con toda su información.

1
Commit de Cambios
Se realiza un commit de los archivos modificados con un mensaje descriptivo que explica los cambios realizados.
git add [archivos]
git commit -m "Mensaje descriptivo del commit"
2
Ejecución del Hook post-commit
Automáticamente se ejecuta el hook .git/hooks/post-commit que captura la información del commit recién creado.
Información capturada:
• Hash completo del commit
• Autor (nombre)
• Email del autor
• Fecha y hora del commit
• Mensaje del commit
3
Actualización de git_history.txt
El hook agrega una nueva línea al archivo git_history.txt con el formato: hash|author|email|date|message
Formato:
3168b1be66503216339d71d5b6e6292ec3217bf3|Ubits|ubits@macbookpro.lan|2025-12-02 15:08:34 -0500|Update: Actualizar changelog con últimos cambios
4
Actualización de Datos Embebidos
Se ejecuta el script update-changelog-html.js que lee git_history.txt y actualiza el array realCommits en changelog.html.
Proceso:
1. Lee todas las líneas de git_history.txt
2. Parsea cada línea en un objeto commit
3. Genera el array JavaScript con todos los commits
4. Reemplaza el bloque realCommits en changelog.html
5
Push al Repositorio
Se ejecuta el script git-push-with-changelog.sh que hace push de los commits al repositorio remoto en GitHub.
./git-push-with-changelog.sh
Acciones:
• Hace push de los commits al repositorio
• Sincroniza commits remotos con git_history.txt
• Actualiza datos embebidos si hay cambios
• Hace commit y push de los archivos actualizados
6
Carga del Changelog
Cuando se abre changelog.html, la función loadChangelog() intenta cargar los commits desde GitHub o usa los datos embebidos como fallback.
Orden de carga:
1. Intenta cargar desde GitHub (git_history.txt)
2. Si falla, intenta cargar localmente
3. Si falla, usa datos embebidos (realCommits)
7
Parsing de Commits
La función parseGitHistory() convierte cada línea del historial en un objeto commit con toda su información estructurada.
Estructura del objeto commit:
• hash: Hash corto (7 caracteres)
• fullHash: Hash completo
• author: Nombre del autor
• email: Email del autor
• date: Fecha y hora del commit
• message: Mensaje del commit
8
Renderizado de Cards
La función renderCommits() crea una card .changelog-item única para cada commit, validando que no haya duplicados y que toda la información esté presente.
Validaciones:
• Verifica que el commit tenga hash válido
• Evita duplicados usando Set de hashes
• Valida que el mensaje exista
• Maneja casos donde autor/email estén vacíos
• Agrega atributo data-commit-hash único
Ejemplo de Card Generada:
Título: Update: Implementar múltiples teams y funcionalidad hide section
Hash: b5bc3fb
Autor: Ubits (ubits@macbookpro.lan)
Fecha: 2025-12-02 15:08:25
Enlace: GitHub commit link
9
Inserción en el DOM
Todas las cards se insertan en el contenedor #changelogContainer y se actualiza el contador de commits totales y la fecha de última actualización.
Resultado:
• Cada commit tiene su propia card única
• Las cards están ordenadas (más reciente primero)
• Se muestra el total de commits
• Se registra la fecha de última actualización
• Se valida que el número de cards coincida con commits
10
Verificación y Visualización de la Card del Último Commit
PASO MANDATORIO ANTES DE FINALIZAR: Se verifica que el último commit creado tenga su card correctamente generada y se muestra su información para confirmar que el proceso se completó exitosamente.
Proceso:
1. Se obtiene el último commit usando git log -1
2. Se verifica que el commit esté presente en git_history.txt (debe ser la primera línea)
3. Se verifica que el commit esté presente en realCommits (debe ser el primer elemento del array)
4. Se confirma que la primera card en el DOM corresponda al commit más reciente
5. Se valida que el ordenamiento sea correcto (más reciente primero)
6. Se muestra la información del último commit (hash, mensaje, autor, fecha)
7. Se valida que el enlace a GitHub funcione correctamente
Validaciones CRÍTICAS:
• El hash del último commit debe ser la primera línea en git_history.txt
• El último commit debe ser el primer elemento en realCommits
• La primera card en el DOM debe tener el hash del último commit
• La card debe tener el atributo data-commit-hash correcto
• El mensaje del commit debe coincidir
• La fecha y autor deben ser correctos
• El ordenamiento debe ser descendente (más reciente primero)
• El enlace a GitHub debe ser válido
⚠️ Si la primera card no es el último commit, hay un problema de ordenamiento que debe corregirse
